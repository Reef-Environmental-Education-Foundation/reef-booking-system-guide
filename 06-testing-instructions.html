REEF Ocean Explorers Booking Workflow — Staff Pilot Handoff

Staff Testing Instructions

How to test safely during pilot week, without touching real bookings or real customers

2026-09-08

Where to Test

There is no separate sandbox base. Test directly in the real REEF Bookings | PILOT base, using the new "ZZZ STAFF TEST (Sandbox)" view on the Bookings table — a filtered view showing only records whose Booking Name contains ZZZ STAFF TEST.

→ Open the ZZZ STAFF TEST (Sandbox) view

This is deliberate, not a shortcut: a separate duplicated base would be disconnected from the live Zaps, the review gate, and EPO, so anything you found there wouldn't tell you how the real system behaves, and a bug you hit there might not even reproduce in the real base. Testing in the real base, clearly labeled, is what actually exercises the live automations.

How to Create a Safe Test Record

  1. Name it starting with ZZZ STAFF TEST — exactly that text, case-sensitive — in the Booking Name field (e.g. ZZZ STAFF TEST — Jane Smith — pilot week). This is what makes it show up in the sandbox view and clearly marks it as not-real to anyone else who opens the base.
  2. If you're testing the full intake path, create the matching EPO record with the same ZZZ STAFF TEST prefix in its Event Name, so it's identifiable end-to-end across EPO, Bookings, and the Asana task Zap 1 creates for it.
  3. Don't reuse or edit the older ZZZ TEST records already in the base (Riverside Academy, Sunridge Community Center, the sync-verification record, "ZAP 3 TEST BOOKING"). Those are a separate, older set of build/QA artifacts — leave them alone.

What to Test

  • Sample inquiry intake (EPO record → Asana task via Zap 1)
  • Sample booking pricing (checking "Ready for REEF Bookings" → Bookings record via Zap 2)
  • Proposal generation — System 1 (the live Google Sheet/Doc path)
  • Proposal generation — System 2 (the HTML page) — clearly label this as a test in any notes; it's not customer-facing
  • The "Ready to Move Forward" and "Request a Change" buttons on System 2 — expect these to log a response but trigger nothing further (the CTA webhook is still blocked); that's expected, not a bug
  • Confirmed-page generation, if you have access to run the pipeline — otherwise leave this to the build owner
  • The review gate: after generating a proposal/contract package for your test booking, confirm an Asana review task actually appears, assigned to Rose, with the right links attached — and that it's clearly marked as a test needing no real action
  • Moving a test booking to Confirmed, and confirming the EPO + Asana sync actually fires (Zap 3)

Record anything confusing or broken in the "Bugs and Confusing Moments" section of the pilot Asana project — see the Bug-Reporting Process.

Zapier task budget — don't churn records. REEF is on the Zapier Pro plan: 750 tasks/month, resetting Oct 8, 2026. Every real or ZZZ STAFF TEST record that flows through Zap 1, 2, or 3 consumes plan tasks. A handful of clean passes through the flow is enough to confirm it works — don't loop the same test record through repeatedly just to watch it fire again. If you need to retest something, reuse an existing test record rather than creating a new one each time.

What Staff Should Not Touch

  • Don't edit real (non-test) booking records just to try something out.
  • Don't rename or delete Airtable fields, views, or automations.
  • Don't run the "Publish Booking Package" GitHub Action against a real customer's booking without a completed review task already in place.
  • Don't send a System 2 proposal link to a real customer.
  • Don't hand-edit the automation-owned Bookings fields: EPO Record ID, Asana Task ID, Agreement Sent Date, Follow-Up Reminder Sent. Zapier writes these; editing them by hand can break the duplicate-check logic.
  • Don't delete any record, real or test — REEF's standing rule is never delete, note issues instead. If a test record needs cleanup, flag it to Martha or Rose rather than removing it yourself.
When in doubt, test it — that's the point of pilot week. If something feels ambiguous or you're not sure whether an action is safe, ask in the Decisions Needed section of the Asana project rather than guessing on a real record.
See the Bug-Reporting Process for how to log what you find, and the First-Real-Booking Checklist for what happens once testing is done and a real booking goes through.
